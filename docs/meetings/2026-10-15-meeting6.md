**날짜**: 2026-10-15 · **성격**: **사용자 소집 회의. 제안이며 디자인/제품 승인 아님.** 소스·설정·빌드 수정 없음(분석/의견만).

## 회의 범위 및 전제

**명시 범위**:
- **5차 회의의 기능·기술 계획은 그대로 유지**: 반응형 Option A, Casual/Extend, Calendar/Quick Checklist, 토큰 단일화, 대표 3종(media/cpu/clock) 진행, Clock 중단, 사용자 최종 승인 게이트
- **이번에는 "시각 방향"만 재검토**: 컬러 시스템 + 화면 구성(표면·투명도·정보 위계·조작 배치)
- **컬러·표면을 전면 변경 전제**: 기존 승인 대표(Media/CPU P0, 크림 계열)는 새 시각 방향 확정 시 **재작업 대상 가능** (범위·소급 여부는 Codex 판단, 기존 게이트 유지)

**컬러 후보군 (P1~P4)**:
- 각 팔레트를 **라이트·다크 양쪽**에서 평가 (1번=라이트, 2번=다크 식의 조합 대응이 아님)
- P1 (Lavender Blush/Mist 저채도 라벤더·모브), P2 (Dust Grey 뉴트럴+세이지), P3 (Ink Black 다크 남보라+비비드 레드), P4 (Midnight Violet 딥 바이올렛·틸·허니듀)

**레퍼런스 (R1~R3)**:
- R1: 다크 반투명 보드 + 작은 반투명 캘린더 (상단 빗금 배제, 투명도·색 조합 원칙만 추출)
- R2: 사용량 카드 (정보량 과다 제외, 투명도·컬러 위계만 추출)
- R3: 정돈된 세션 카드 (우선순위 최하)
- **재현 금지**: 특정 화면을 재현하지 않음. 가독성·정보 위계·조작 편의성에 관한 원칙만 추출

## 에이전트별 의견 및 권고안

### 1. Codex (시각·StyleSeed 리드) — 디자인 시스템 전략

**핵심 권고 3건**:

1. **컬러 후보 우선순위**: P4를 우선 검토, P2를 중립 대안으로 제안
   - **P1**: Light는 부드러운 개인 공간, Dark는 차분한 모브. 원래 5색만으로는 본문 대비 부족. 파스텔로 전체를 채우면 위계·개성 평준화.
   - **P2**: 양 모드에서 사진·그래프와 충돌 적음. 확장 기반 안정적이나 회색만으로 감성 약함.
   - **P3**: Light는 잉크 글자 명료, Dark는 시스템 정보에 어울림. 빨강은 경고와 혼동 → 역할 제한. Memo/Breathe까지 강한 색 강요 금지.
   - **P4** (권고): Light는 허니듀·절제된 틸, Dark는 깊은 표면·밝은 글자 조화. 시스템·일상·도구 25종으로 확장 좋음.

2. **표면·투명도 정책**: R1의 색·투명도 조화, R2의 글자색 중요도 구분 추출
   - 배경만 투명하게, 글자·아이콘·그래프는 선명함 유지
   - Casual의 None/Low/Mid/High, Extend 수치 조정 (5차 계획) 유지
   - 입력·소형 글자 많은 면은 High 권장
   - 밝고 어둡고 복잡한 배경에서 실효 대비 검사 필수, 필요 시 국소 받침은 사용자 승인 후 설계
   - **블러는 필수 아님**: Claude의 구현 비용·리스크 판단 기다림

3. **독자적인 위계와 범위**: R1~R3를 재현하지 않고 원칙만 적용
   - Media 정보→진행률→조작, CPU Big 현재값→추세 구조 보존
   - 새 보조 글자색으로 위계 보완, 소형 글자 4.5:1 대비 희생 금지
   - AQI·충전·경고의 의미색은 브랜드 강조색과 분리
   - R2의 과한 정보량 계승 금지, 크기별 정보 계약 유지
   - R1 상단 빗금 제외, R3 정렬 원칙은 최하 우선순위
   - 범위: 사용자 팔레트·파생색 선택 → 승인 → Media Mid Light/Dark 대표 → PNG·QA·확인 → CPU/Clock 역할 차이 → 25종 순차 적용

**StyleSeed 갱신 (현행 규칙 유지)**:
- 선택·제작·실제 QA 뒤 채택된 개선만 Codex가 승인된 ThemeService 역할·ruleset/brief·PNG/spec에 반영
- 해당 bundle/manifest/index 해시 함께 갱신
- 일반 Muted와 반전 Clock 전용색을 일괄 치환 금지
- 후속 확장은 새 버전 결합 끝까지 대기 또는 구버전에 명시적 고정
- **Impeccable·생성 palette는 색상 권위가 아님** (StyleSeed = 승인된 단일 권위)

**자산 권한·유사성**:
- 기존 Pretendard/Nunito OFL, Fluent MIT 확인 완료
- 실제 배포 자산의 출처·버전·해시와 저작권·라이선스 고지 대응 필수
- R1~R3 원본·출처·권한 미확인 → 이미지·고유 자산 미사용
- 최종 시안에서 전체 배치·고유 모티프·서체 리듬·조작 구성을 원본과 비교

### 2. Claude TL (기술·구현 리드) — WPF 구현 영향

**새 컬러의 ThemeService·XAML 영향**:
- **토큰 재정의 규모**: P1/P2는 점진 적용 가능 (기존 12 토큰 확장, 비용 낮음), P3/P4는 토큰 전면 재구성 필수 (비용 높음)
- **XAML 적용 경로**:
  1. ColorToken enum 확장 (선택된 후보별)
  2. ThemeService Light/Dark 세트 정의
  3. Controls.xaml 기본값 갱신
  4. 기존 XAML hex 리터럴 정리 (Step 조사 후)
  5. 대표 3종 brief 갱신 → 재작업

**투명도·블러·다크 모드 WPF 구현**:
- **투명도**: 기본 지원, 비용 낮음, 리스크 낮음 (Opacity 토큰 추가, 기존 구조 유지)
- **블러**: WPF 기본 미지원. D3D/SharpDX 구현 시 매우 높은 비용·DPI 복잡도·성능 리스크. **블러 미지원으로 보수 결정, 반투명 오버레이로 대체 권장**. (비용/리스크 높으므로 사용자 명시 승인 필수)
- **다크 모드**: Light/Dark 2세트 이미 구현. 새 컬러 후보에서 P3/P4는 Light/Dark 비대칭 → 매핑 복잡도 증가

**점진 적용 경로**:
1. Phase 1 (토큰 재정의): 1~2주 (P1/P2 선택 시), 2주+ (P3/P4)
2. Phase 2 (투명도 세분화): 1주 (선택사항)
3. Phase 3 (블러): 사용자 명시 승인 필수 (고비용 항목)

**5차 기술 계획 유지**: Casual/Extend, 반응형 Option A, Calendar/Checklist 일정 변경 없음

**현황 실측**:

**R1~R3 장단점·원칙** (재현 없음):

### 4. Assistant (QA) — 측정 방법

**대비·가독성 정량 측정**:
- WCAG 2.x: 본문 ≥4.5:1, 대형 ≥3:1, 비텍스트 ≥3:1
- 측정 대상: Text↔Surface, Secondary↔Surface, Accent↔Surface, Accent-Text↔Accent Fill, Border/Track↔Surface, Focus Ring↔Surface
- **절차**: 토큰 hex로 결정적 계산 (Python/Node), 반투명은 배경 합성색으로 계산, 실패 명시 (doctor green 조작 금지)

**정보 위계 정량 측정**:
- 3단 위계 (primary/secondary/muted)를 축으로 고정
- font size·weight·대비 tier로 단조 감소 확인
- 저대비로 흐리지 않고 size/weight/spacing으로 위계 구성

**외부 자산 권한 표기**:
- 자산 종류·파일명·출처·라이선스·파일·취득일·사용 범위·재배포·대체 여부
- Pretendard/Nunito/Fluent 기존 번들 유지, 새 폰트 추가 시 라이선스 동봉
- 이미지/사진: 라이선스 확인 불가 시 사용 금지
- **생성 palette/StyleSeed 산출물은 Nook import 금지**

**레퍼런스 유사성 체크**:
- 전체 컴포지션·고유 모티프·색 정체성·타이포 리듬·조작부 배치 (픽셀 일치율로 판정 금지)
- 원칙만 추출했는가 확인, 특정 화면과 구별되는 대표 요소 기록

### 5. MiMo (프로덕션) — 실현성

**기술별 가능성**:
- **반투명**: 가능 (hex alpha). 합성 결과는 Pencil 배경 기준 (실제 앱 배경 증거 아님)
- **그라데이션**: 가능하나 ThemeService flat 토큰과 충돌 → Codex 승인 필수
- **블러**: 형태만 가능. WPF Acrylic/Mica와 동일성 없음 (미검증)
- **그림자**: 가능. 색·반경은 토큰 외 (승인 대상)

**제약**:
- Alpha는 hex alpha 채널 전용 (이중 감쇠 금지)
- 반투명 표면에 flat 대비 공식 미적용 → 합성색 기준 재계산 필수
- P1~P4 라이트/다크는 지정 프레임만 (자동 매트릭스 금지)
- R1~R3는 원칙 추출만 (재현 거부)
- Media/CPU P0 재작업은 색·표면만 교체 (기하·서체·게이트 유지, 자동 소급 없음)

## 회의 결론

### (a) 합의된 결론 (Agreed Conclusions)

1. **시각 방향 재검토 대상 확정**: P1~P4 컬러 후보를 라이트·다크 양쪽에서 평가

   - 각 팔레트를 독립적으로 평가 (1-to-1 모드 매핑 아님)

2. **표면·투명도 원칙 확정**:
   - 배경 투명도로 계층감, 글자색으로 중요도 구분
   - Casual None/Low/Mid/High, Extend 수치 조정 유지
   - 블러는 필수 아님 (비용/리스크 높음)

3. **정보 위계 설계 원칙**:
   - R1~R3 화면을 재현하지 않음 (원칙만 추출)
   - 기존 구조 (Media 정보·진행률·조작, CPU 현재값·추세) 보존
   - R1 빗금 배제, R3 최하 우선순위

4. **5차 기능·기술 계획 유지**: Option A, Casual/Extend, Calendar/Checklist, 토큰 단일화, 대표 3종, Clock 중단, 사용자 게이트

5. **StyleSeed 원칙 재확인**: ThemeService = 승인된 단일 색상 권위, Impeccable/생성 palette = 디자인 크리틱 (Codex 선택), 미검증 항목은 import 금지
